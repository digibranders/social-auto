# Runbook

Everyday chores and what to do when an alert arrives. Written so anyone can follow it, with or without Claude.

## How it fits together

| Piece | Where | Does what |
|---|---|---|
| **Content engine** | `scheduler/engine`, on the server (timer `social-auto-weekly`, Mondays 10:00 IST) | Reads a client's website, writes posts, draws posters, saves them to GitHub `main`. |
| **Publisher** | `publisher/`, service `social-publisher` | Posts every day, renews tokens, sends alerts, serves the private status feed and the product API. |
| **Dashboard** | `dashboard/`, service `social-dashboard`, at `https://social.digibranders.com` | Calendar behind a login: what is scheduled, published, missed. Posts that have not gone out yet can be edited (caption, hashtags, picture) or reverted. |
| **Old Vercel projects** | `social-publisher`, `social-dashboard` on Vercel | Being retired. Never let their cron and the server's timers post at the same time. |

Flow: weekly job writes the posts into the repo checkout on the server and pushes to GitHub `main` → the publisher reads the new schedule from the same folder (no deploy) → the publisher posts daily → the dashboard reads the publisher's status feed.
Work on a branch, open a pull request, merge into `main`, then run `deploy/scripts/deploy.sh` on the server. See `deploy/README.md`.

## Alerts (push, via ntfy: topic in `ALERT_NTFY_TOPIC`)

| Alert | Meaning | What to do |
|---|---|---|
| **Instagram post failed** | Today's post did not go out. | Read the error. Token problems: see "Replace the Instagram token". A post stays due for 20 hours: after fixing, re-send it (ask Claude) or post it by hand (poster and caption are in the dashboard). |
| **Schedule running low / No scheduled posts left** | 7, 3, 1 or 0 posts left. | The Mac has probably been off on Mondays. Run the weekly job by hand (below). |
| **Instagram token renewal failed** | Weekly renewal could not extend the token. | Replace the token (below) before it expires. |
| **Instagram token changed** | Instagram returned a different token while renewing. The saved one still works until it expires. | Replace the token (below). |
| **Weekly content job failed** | The Monday job on the Mac stopped. | Read `~/Library/Logs/social-auto/weekly.log`, fix, run it by hand. |

## Chores

### Replace the Instagram token
1. developers.facebook.com → app **scheduler** → Use cases → Manage messaging & content on Instagram → Customize → **API setup with Instagram login** → **Generate token** for the account. Approve the login in Instagram if it asks.
2. Save the token in a private file (never commit or paste it anywhere else), then from the repo root:
   `printf '%s' "$TOKEN" | vercel env update INSTAGRAM_TOKEN production --sensitive --yes`
3. Vercel only applies a changed secret to **new** deployments: Vercel → `social-publisher` → Deployments → latest production → ⋯ → **Redeploy**.
4. Check: `curl -H "Authorization: Bearer $CRON_SECRET" "https://social-publisher-lovat.vercel.app/api/cron?dryRun=1&post=<post id>"` should answer `dry-run-ready`.
5. Delete the private file.

### Connect a client's Facebook Page
The client first makes your Facebook account an admin of their Page (Page settings, Page access, "Facebook access"; full control is not needed). Accept it, then in the dashboard click **Connect Facebook** (as that same Facebook account), choose "current Pages only" and tick the Page. The Page token is saved **encrypted** in the private store (`channels.json`) and never shown. From the next scheduled post on, each post also goes to the Page; posts from before the connection are not sent. Instagram and Facebook are independent: one failing does not stop the other, and each failure sends its own alert. To disconnect a Page: POST `/api/channels` with `{"remove": "facebook:<page id>"}` and the edit secret (a button is not built yet). While the Meta app is unpublished, only accounts with a role in the app can connect.

### Run the weekly job by hand
`~/social-auto-runner/scheduler/engine/scripts/weekly.sh`, or `launchctl kickstart gui/$(id -u)/com.56steve.social-auto.weekly`. The log is `~/Library/Logs/social-auto/weekly.log`.
The job works in `~/social-auto-runner`, a separate checkout of `main`; it refuses to run if that checkout has local changes or is not on `main`.

### Everything on the VPS
Publisher and dashboard can run as two Node servers on the VPS instead of Vercel (see `deploy/README.md`): systemd services `social-publisher` and `social-dashboard`, timers `social-cron` and `social-refresh` (replacing Vercel Cron), data in `/var/lib/social-auto`, settings in `/etc/social-auto/*.env`. Logs: `journalctl -u social-publisher -u social-dashboard -u social-cron`. Update with `deploy/scripts/deploy.sh`. Never run the Vercel crons and the server timers together, or a post can go out twice.

### Which pages of a site are read
The engine scores every internal link on the homepage and reads the best few (`scheduler/engine/src/pages.ts`). Nothing in it is built for an industry. The scoring uses generic page types (pricing, about, services, FAQ and similar), where the link sits (navigation or footer), the link's text, how deep it is, and, for pages whose name the list does not know, the words the site uses about itself on its own homepage (title, description, headings, repeated words), in any language. Legal, account and housekeeping pages score low.

The budget is shared in two rounds: first the best page of each kind of page the site has (an offering, About, FAQ, proof such as case studies), then the rest by score, where each extra page from one section costs a little more (less for offering pages), so a catalogue of look-alikes cannot fill it. A kind a site lacks leaves its place free, and pages below the minimum score are never filler. A shared prefix such as `/en/` or `/products/` does not make every page one crowded section.

Regional copies of a page are consolidated, keeping the plain address, then the site's own language and region; a page that exists only once stays eligible. After fetching, a page that is thin, a duplicate (same canonical address or text) or unreachable gives its place to the next best page. `robots.txt` blocks are never fetched and use none of the budget. For every client the choices are saved as `brands/<client>/pages.json` with each score and reason.

| Setting | Meaning |
|---|---|
| `CRAWL_MAX_PAGES` | The most pages read per site, the homepage included. Whole number from 2 to 40, default 10. Nonsense is refused. |

A client's own vocabulary and thresholds (`RankingConfig`: weights, minimum score, section penalties, coverage share, catalogue size) can be passed as configuration without code changes. Real-site test fixtures can only be saved for sites on `scheduler/engine/src/fixtures/approved-sites.json`.

### Claims about a client come with their source
The brand profile's proof points are claims the site really makes (`scheduler/engine/src/claims.ts`). The model proposes each with the page it comes from and the exact words copied from that page; the engine then checks, with no AI involved, in three independent layers:

1. **The source is real.** The page was read and the quote is on it (compared through spacing, case, curly quotes and dashes). The page's fingerprint and fetch time are recorded, and a page that changed since is flagged for re-checking.
2. **The quote supports the claim.** Every number, unit, currency, billing period and qualifier ("from", "up to", "more than") of the claim matches the quote; a negation either way (the quote says "do not guarantee", or the claim says "never" against a plain quote) fails it; a claim that shares little wording with its quote is held for review.
3. **The rules for that kind of claim hold.** A superlative or a guarantee must be made by the source itself; a claim about "now" needs a recently read page; list sizes like "3 ways" are not facts to prove; ordinary wording needs no measurable proof.

Each claim ends `verified`, `uncertain` or `rejected`, with a confidence worked out from the checks that passed (never from the model) and the reasons. Only verified claims go into `brand.json`; all of them, with sources and reasons, are saved in `brands/<client>/evidence.json`. A site with nothing verifiable simply has no proof points. Every word list is a setting (`ClaimConfig`), none belongs to an industry, and a verbatim match alone is never enough: it proves the words are on the page, not that they support the claim.

**The claim gate on post copy.** When posts are written, every sentence of the headline, subline and caption is checked before any picture is generated. A number (digits or spelled out, so "ten hours" counts), price, percentage, billing period, superlative, guarantee or deadline must be stated by one verified proof point, with the same figure, currency, period and qualifier. Facts borrowed from two different claims are turned back too. List-size numbers ("3 ways") and call-to-action words ("today", "now") are not claims. A sentence that fails is reported to the model by field and wording and it rewrites the post; if it fails again the plan stops, so no picture is paid for. With no proof points, plain copy still passes and any figure is blocked. Vague endorsements need proof like a figure does ("trusted by many", "thousands of", "award-winning", "industry-leading"), while "best practices" is not a superlative; a deadline ("ends", "until") is checked even though "today" alone is not; product names and standards ("iPhone 17", "ISO 27001") are identifiers, not figures, but Title Case and all-caps headlines keep their figures; Indian digit grouping (1,00,000) reads as one number. Copy the checker cannot read (a non-Latin script, or a decimal comma such as 1.000,50) is reported as `unchecked` and turned back, never passed silently; other Latin-script languages are not covered by the English word lists yet. The word lists are the same `ClaimConfig` settings plus `vague`, `neutralPhrases` and `plainCapitalWords` (`src/copy-gate.ts`).

**Where the logo came from.** `brand.json` carries a `logoSource`: whether the logo is the site's own picture, the site icon with the name beside it, or the name alone; the page it was found on; the exact picture address; the saved file, type, size and `sha256`; the time; and every address tried in order with its outcome (`used`, `failed: 404`, `failed: not an image (text/html)`). A wrong logo is traced from there to its address. Profiles made before this have none and still load.

**What the brand is, and what to do next.** `brand.json` carries an `identity`: one plain sentence (at most 90 characters) saying what the business is, taken only from the site. The reader proposes up to three candidate lines with their quotes; each must pass the same source checks as a proof point, and the ladder picks the best verified one: a line you approved, then the homepage, an about page, an offering page, the page title and description (`metadata:<origin>`). A line must also read as a description, not a slogan: a command or motto ("Think different", "Discover the difference") is turned back even when the site says it, and the identity records whether it is `descriptive` (it joins a thing to its purpose or audience, "software for small businesses") or only `uncertain`. Candidates are ranked by what they say first and by where they come from second, so a precise service-page line beats a vague About line; `/en/`-style locale roots count as the homepage; and the page title and description are separate sources, so a quote cannot span them. With nothing verified the identity is the brand name alone, marked `name-only`, and no category, audience or capability is invented. The `cta` is chosen by code from the links of the homepage. Every link that could mean an action is scored by where it sits (main navigation over body over footer), whether its visible text or only its address says it, and how short it is; the order of the rules (book, demo, quote, pricing, shop, menu, services, get started, donate, contact, blog) only settles ties. Article titles, deep editorial addresses and ambiguous links ("floor plans", "store locator") never count, and a site whose language the rules do not cover gets the fallback. The chosen action always names a real link as its evidence; with none, it is "Visit" and the real address. The model no longer writes the call to action. Every poster format shows the identity line (unless name-only) under the logo and the action with the address in the opposite corner. The action rules and the "about" words are settings (`src/cta.ts`, `src/identity.ts`).

**Content pillars and the weekly mix.** Every post belongs to a pillar: `problem` (a need the brand's offer meets), `education` (one concept or process explained from a verified proof point), `proof` (one verified proof point, unchanged), `offer` (what the profile says is offered) or `story` (how the brand works, from its verified identity line). Code, not the model, gives each slot its pillar (`src/pillars.ts`): the pillar furthest below its share this week (uses divided by weight), then below its share in recent weeks, then unused for longest, never the same twice in a row. Equal weights mean a week with no more posts than pillars never repeats one and longer weeks stay within one post of balanced; a weight is a setting per pillar, and 0 switches it off. The next week carries on where the last stopped (`history.json` records the pillars of each accepted week). A pillar is available only when its evidence exists: `problem` and `offer` need an offer, `education` and `proof` need a verified proof point, `story` needs a verified or approved identity (a name-only identity does not count); with none available the plan stops with a clear message instead of inventing content. Education and proof posts are each assigned one proof point, rotating through the list, and are turned back to the model unless built on it: its words must appear in the copy, and every sentence that touches it is checked for numbers, prices, units, billing periods, qualifiers and negation (so "guarantees" cannot pass for "does not guarantee"); a faithful paraphrase that keeps the figures passes, one with no figures and different words cannot be confirmed and is turned back. The claim gate still applies to every post. Each post in `week-NN.json` records its `pillar`. The pillar set, needs and weights are settings. Not covered yet: separating a marketplace's own claims from its sellers' claims, and consequential advice in regulated fields beyond what the verified proof points say.

**Hooks.** Every post is also given a hook, the way its headline opens: `question`, `benefit_statement`, `numbered_list`, `direct_statement`, `contrast`, and, only when the profile holds the evidence (a verified before and after, source-backed steps, a common belief with its correction), `before_after`, `how_to` and `myth_fact`. Today the profile holds none of that evidence, so a week rotates the first five. Code picks the hook together with the pillar (`src/hooks.ts`): a hook must suit the pillar (a settings table of strong, conditional or weak fits), have its evidence and a weight above zero; among those the hook furthest below its share this week wins, then in recent weeks, then the one whose pairing with this pillar was not used lately, then the better fit. The hook just used is skipped unless it is the only one. The prompt tells the writer "Post N (pillar, hook)" with the hook's brief. Checks that code can verify are hard: a question ends in a question mark and a statement does not; a numbered list starts with its number (2 to 5), returns that many distinct, non-empty `listItems`, and the items are checked by the claim gate and added to the caption. Repetition is a recorded warning, never a retry: the same first three words as one of the last ten headlines, or a very similar headline among the last twenty; both are skipped, and said to be, for scripts written without spaces. Whether a headline truly follows its hook is for a later model review. A headline that fails its hook is sent back; on the last try it is replaced by a complete, already-supported line (a post built on a proof point falls back to that whole proof point, other posts to the identity line), never a cut-off quote, and the plan fails before any picture if none fits. Each post records its `hook`, and `requestedHook` when a fallback replaced it, so rotation follows what was really published; `history.json` stores each week's hooks and normalized headlines. The hook set, fit table and weights are settings.

**Repeated ideas.** Every post is written with a structured `concept`: its subject, the angle, the one message, and what the picture shows (visual subject, action, composition). A missing or malformed concept is sent back, never skipped. Before any picture is made each draft is compared (`src/concepts.ts`) with the brand's last 40 accepted posts and with the earlier posts of its own plan: the same message on the same subject and angle (compared as content words, so "do not lose data" is not "lose data" and "prevent" is not "recover"), an identical headline, or the same proof point for the same pillar from the same angle within six posts is a repeat that needs a new idea, whatever hook or pillar carries it; a repeated picture idea (same visual subject, action and composition) asks only for a new picture; the same subject from a different angle is allowed. Words a brand uses in most of its posts count for less once ten posts exist, and only words the brand has listed as equivalent are merged (`synonyms`), never guessed. The same subject and angle with a new message soon after is allowed with a recorded warning, and after 14 days it is a labelled `revisitOf` the older post. Concepts in a script written without spaces cannot be compared and are recorded as unchecked. A repeat is sent back once; if the second try still repeats, that post is left out, so a narrow brand gets fewer posts, never a duplicate: the plan then carries `insufficientConcepts` (requested, produced, reasons) and the autopilot says so, and with no new idea at all the plan stops with `insufficient_distinct_concepts` before any picture. The prompt shows the writer the last ten concepts, but the check, not the prompt, decides. History keeps each accepted post's concept record, written only after the plan is accepted. Windows, thresholds and word lists are settings. Not built: planned series (a repeated subject across numbered episodes); a series must never be a flag the model can grant itself, so it needs an approved content plan first.

### How a week's posters differ
Each post gets a poster format from a fixed rotation in code (`scheduler/engine/src/creative.ts`), so a week never looks like one repeated image: **type** (a big headline, no picture, so it costs nothing), **illustration**, **still-life** and **isometric**. Neighbouring posts always differ, also across weeks. The model only suggests an idea per post (an object or abstract scene, never people); the code wraps it with the format's look, the brand's own colours and the no-text rule. The logo is the site's own logo picture, else its icon with the name beside it, else the name alone. Plans written before formats existed still render as the old photo posters.

### How the engine reads a client's website
- It identifies itself as `SocialAutoBot/1.0 (+https://social.digibranders.com)` and respects the site's `robots.txt`. A site that asks bots not to read it is not read, and the error says so.
- It reads public addresses only: every address a name points to, and every redirect, must be public (no `localhost`, private networks or cloud-metadata addresses), on the standard web ports, with a size cap.
- Up to 8 pages, about 3,000 characters each, preferring about, services, pricing and FAQ pages. A page that arrives almost empty (a site that builds itself in the browser) is opened in Chrome instead, up to 4 pages per run.
- If the site holds too little text even after that, the run stops with "gave too little to read" instead of writing weak posts.
- If no logo can be downloaded, the brand's name is drawn as a text logo. The brand profile also carries a short "visual style" (palette in words, mood) that goes into every picture prompt, and the fade over each picture uses the brand's own light background colour.
- Known limit: Chrome follows redirects and scripts on its own, so the Chrome step is only used after the address passed the public-address check and should not be pointed at addresses you do not trust.

### Run the content engine on a Linux server
The engine runs on a Mac or on Linux. On Linux it needs Node 24, Google Chrome (`google-chrome`) and ImageMagick (`convert`, which replaces the Mac's `sips`). Settings are environment variables, so a server needs no edits to the code:

| Variable | Meaning |
|---|---|
| `CHROME_PATH` | Chrome's location. Defaults to the Mac app on a Mac and `google-chrome` on Linux. |
| `CHROME_NO_SANDBOX` | `1` if Ubuntu refuses Chrome's sandbox for a normal user. The engine only opens pages it built. |
| `SOCIAL_AUTO_ENV` | A keys file (`POLLINATIONS_API_KEY`, `SCHEDULER_API_KEY`, `ALERT_NTFY_TOPIC`). Keys already in the environment win, so a service can supply them directly. Default `scheduler/upstream/.env`. |
| `SOCIAL_AUTO_LOG_HINT` | Where an alert tells you to look for the log. |
| `OPENAI_API_KEY` | The organization's OpenAI key. When set, OpenAI writes the posts and draws the pictures. Never commit it. |
| `OPENAI_TEXT_MODEL` | Default `gpt-6-luna` (cheapest; `gpt-6.1-terra` is the next step up if the writing needs it). |
| `OPENAI_IMAGE_MODEL` | Default `gpt-image-2.5-sunburst`. |
| `OPENAI_IMAGE_QUALITY` | `low`, `medium` (default) or `high`. Higher costs more per picture. |
| `OPENAI_MAX_IMAGES_PER_RUN` | Default 40: the most pictures one run may order from OpenAI. |
| `USAGE_LOG_FILE` | Where the engine adds one line per AI call (client, post, what it was for, tokens, dollars). The publisher reads the same file, which is how the dashboard's Cost tab shows each client's spend. On the server: `/var/lib/social-auto/usage.jsonl`, set both in the engine's keys file and in `social-publisher.service`. Unset, nothing is recorded. The amounts are estimates from OpenAI's token counts and published prices; the OpenAI usage page is the real bill. |
| `AI_PROVIDER` | `openai` or `pollinations`. Default: OpenAI when its key is set, else Pollinations. |
| `AI_FALLBACK` | `on` lets the other provider stand in when the main one fails (it needs the other provider's key). Default off: a failed paid request is an error, never a quiet switch to a free model. When a backup does answer, the run prints a `WARNING` line at once, ends with a `FALLBACK` summary, and the usage log marks those calls (`fallback`, `requestedModel`, `fallbackReason`). |
| `POLLINATIONS_API_KEY` | Pollinations key: the main provider when there is no OpenAI key, otherwise the backup. |
| `POLLINATIONS_IMAGE_MODEL` | The picture model Pollinations uses (default the free `zimage`). Paid models need credit on that account. |
| `IMAGE_COMPOSITION_HINT` | `1` asks the picture for open space where the poster layout puts its text. Off by default, so prompts are not tuned to one model. |

### Edit a post in the dashboard
Open a scheduled post → **Edit post**. Change the caption (max 2200 characters, 30 hashtags) or **Replace picture** (square JPG, max 4 MB), or **Revert to original**. Changes apply at once and are what gets posted at the scheduled time; no redeploy. Posts that are due, published or missed cannot be edited (Instagram does not allow changing a published caption).
Edits live in the private Vercel Blob store `social-publisher-edits` (file `overrides.json` plus `images/`), never in git. If the store cannot be read at posting time the post **fails with an alert** instead of going out unedited. The Monday job does not touch edits; deleting a post's edit (Revert) restores what the content job planned.

### Change or remove a post (in the files)
Edit `scheduler/engine/brands/<client>/week-NN.json` (caption, headline, `imagePrompt`). Delete `out/<client>/week-NN/<id>-bg.jpg` to draw a new picture. Then in `scheduler/engine`: `node src/render.ts --brand brands/<client> --plan week-NN.json`, `node src/export-publisher.ts --brand brands/<client>`, commit, pull request, merge. Do not edit a post whose time has already passed.

### Change how often a client posts
In `scheduler/engine/clients.json`, give the client either `"postsPerWeek": N` (1 to 7, spread evenly: 1 = Mon, 2 = Mon/Thu, 3 = Mon/Wed/Fri, 5 = Mon to Fri, 7 = daily) or exact days, `"weekdays": ["tue", "sat"]` (which wins over the number). Each Monday run adds one week's worth of posts after the last planned one. A change applies from the **next weekly run**; posts already scheduled stay as they are (delete them in the files, see "Change or remove a post", if they should go). A longer gap between posts also makes the queue last longer, so the "running low" alerts come later. The old `"days": N` (N posts on consecutive days) still works.

### Add a client
Add an entry to `scheduler/engine/clients.json` (`site`, `postsPerWeek` or `weekdays`, `time`, `utcOffset`, `target: "publisher"`). The first run builds `brands/<client>/brand.json` from the website: check it. **The publisher currently posts through one Instagram account**; a second account needs support added to the publisher before its posts can go out.

### Dashboard password and sessions
The password is the Vercel variable `DASHBOARD_PASSWORD` in project `social-dashboard`: `vercel env update DASHBOARD_PASSWORD production --sensitive`, then redeploy. Changing `SESSION_SECRET` signs everyone out.

### Art direction contracts (2.1A, not yet wired into posting)
`art-brief.ts` defines the structured brief an art director returns for one accepted post: layout family, hierarchy, headline scale, alignment, text zone, picture direction (or none) and brand-element slots. It carries no colours, coordinates, CSS, accent words or copy, and parsing drops any such keys. `layout-registry.ts` holds six families (typography hero, split composition, full-bleed editorial, feature spotlight, structured information, evidence spotlight), each declaring text zones with headline/subline/list/figure slots, picture slots named for their role, several logo/identity/CTA placements, text and picture limits, required content and a fallback. `validateRegistry` proves the registry is consistent; `checkBriefAgainstFamily` reports structural problems (unknown layout, disallowed zone/hierarchy/role/medium, missing picture slot, unknown or colliding brand slots). Geometry exists for the 1080 square only; 4:5 and 9:16 are named but unbuilt. Nothing renders from these yet: eligibility, variety, the art-director call and fallbacks are 2.1B-2.1D, composable rendering is 2.2.

### Art options and variety (2.1B, not yet wired into posting)
`art-options.ts` decides which art directions are open to a post without any model or image call. Eligibility comes from content, never pillar or industry: a list layout needs at least two distinct list items, an evidence layout needs a verified figure or quotation (figure-first needs a figure the post's copy states and its verified anchor carries), an offering layout needs a post that shares content words with the profile's offer or features; `postFacts` builds these facts from an accepted post. A tenant can switch families off or set weights (0 switches off); the safe family always stays. Text fit is an advisory estimate (`likely_fit`, `uncertain_fit`, `likely_overflow`) that only costs score; non-Latin text is never called an overflow before real measurement. Options are scored as suitability + weighted-share deficit - recent repetition - same composition - fit penalty, then `shortlistOf` returns up to three that differ by family; with one family eligible it returns one option. `planShortlists` plans a weekly batch against the brand's history plus provisional picks and re-plans from the actual choices when `chosen` is passed. Logo, identity and CTA slots are not candidates: `chooseBrandSlots` picks a clean combination that avoids the last two placements. All weights are starting values to tune against real feeds.

### Art director call (2.1C, mocked only, not yet wired into posting)
`art-director.ts` makes one batched model call per weekly plan. The model picks an `optionId` from each post's code-made shortlist and writes the picture's medium (from that option's list), scene, composition, mood and palette use, plus headline scale and alignment. Layout, zone, hierarchy and picture role come from the chosen option; the picture's subject and action are copied from the accepted concept; logo, identity and CTA slots come from `chooseBrandSlots`; colours, coordinates and copy are never the model's. Each post is validated on its own (shortlist, medium, enums, registry, `picture-policy.ts`); valid posts are kept and only failing or missing posts go into one repair call. The whole batch is capped at `maxCalls` HTTP requests (default 2) counting `chatJson`'s own corrective retries, plus a post-count limit, an input-token estimate limit and an optional `maxCostUsd` read from the run's usage tally. Posts still failing come back `unresolved` with reasons for the 2.1D fallback; nothing is committed to history (the provisional `record` of each resolved post is returned). Website text reaches the model only inside a `DATA (untrusted)` JSON block, and the model is told never to follow instructions in it. `picture-policy.ts` holds back generated pictures that ask for baked-in text, numbers, logos, credentials, product screens or real places unless approved material exists; people are allowed. `art-prompt.ts` builds the final image prompt from the concept, medium, palette and the real text-zone geometry, and returns nothing when the picture role is none. No live call has been made; prompt wording and model choice need an approved live review.

### Resolving directions (2.1D, mocked only, not yet wired into posting)
`art-resolve.ts` (`finalizeDirections`) ends art direction before any picture is paid for. Each post becomes `ready` (a validated brief, its image prompt or none, and the provisional record of the ACTUAL choice) or `failed` with coded reasons; the whole batch gets a plan status (`complete`, `pending_render_validation`, `partial`, `incomplete_required_count`, `failed`) from `requestedPosts`, `minimumAcceptablePosts`, `requireExactCount` and `allowPartialApproval`. Resolution order: keep a valid directed brief; mend harmless errors (scale from the family's `scales`, alignment, medium) keeping the model's layout (`repaired`); when the estimate says the chosen option overflows, try another eligible option before anything else and never truncate copy; otherwise the best other eligible option, with the safe family last (`fallback`). A picture the policy blocked is removed (type-led option, no image), not rebuilt. A missing concept visual also gives a no-picture option. Pictures that code must write come from the accepted concept with rotating, per-medium compositions that avoid the previous poster's. Reasons carry severity (`info`, `warning`, `hard`); hard reasons (`missing_headline`, `no_valid_family`, `final_brief_invalid`, `prompt_failed`) reject the post. A post is `direction_ready` only when its fit estimate is likely; otherwise `ready_pending_measurement`. The batch is flagged for review when two or more posts fell back, any picture was policy-blocked, any post failed, or every post fell back. `direction_ready` certifies structure only: the renderer (2.2) must measure text in a real browser (fonts loaded, no clipping, overflow or collisions, minimum size and margins) and reflow, change family or fail; the visual review is Phase 3. Approved-asset ownership checks are not built because no approved assets exist yet.

### Rendering art-directed posters (2.2, real Chrome, no live model or picture calls yet)
A post that carries `art` in its plan file (candidates in the order to try, each with its brief, image prompt and art record) is rendered by `render.ts` through `render-poster.ts`; posts without `art` render exactly as before. Pipeline per post: `compose.ts` builds the page from the registry geometry and the brand's own colours (six composers over shared primitives; text escaped; the planner's `|accent|` spans kept; a content security policy that blocks every network request; pictures decoded synchronously so a capture never shows a half-drawn picture); the page's own script (`measure-script.ts`) waits for fonts and images, finds the largest font size inside each role's range that fits its slot (never truncating), and writes a JSON report that `fit-report.ts` validates and judges (overflow, collisions, content outside the 32px margins, glyphs no font can draw, failed pictures, contrast below 4.5:1, local fonts that did not load are hard failures; system fonts are a warning). A missing or malformed report is a hard failure. Each candidate is measured with a placeholder picture BEFORE any picture is paid for; the first that passes gets its picture, is measured again with it, frozen with the solved sizes and captured at exactly 1080x1080 (`chrome-render.ts`: one temp directory and profile per job, a timeout, cleanup, Chrome version recorded). A failed measurement moves to the next candidate (other eligible options, then the safe family); if all fail the post is `render_failed`, no picture was requested and no file is written. `render_verified` needs local fonts; with system fonts a poster is `capture_complete` and the report says `system_font`. `render-report.json` in the output folder records status, chosen option, solved sizes, warnings, attempts and the Chrome version per post; a failed poster fails the run but keeps the others. Fonts: put verified files and a `manifest.json` (family, weight, scripts, sha256) in a directory and set `FONTS_DIR`; `fonts.ts` refuses a missing, altered or out-of-directory file. No font is bundled yet, so licensing and which fonts to ship are still to decide. Not built: 4:5 and 9:16, pixel-level contrast sampling of the real picture (the scrim and backings are sized for the worst case instead), the visual review (Phase 3), and wiring the planner, art director and resolver into the autopilot so plans carry `art` automatically.

### Running art direction (wired into the autopilot, off by default)
Normal runs are unchanged. `node src/autopilot.ts --site <site> --art ...` adds one batched art-director call after the plan is accepted, then renders with measurement. It runs only when ALL of these hold: the brand's `brands/<slug>/art.json` says `{"enabled": true}` (optionally `"fallbackToLegacy"`, `"maxCostUsd"`, `"maxPostsPerBatch"`); `ART_DIRECTION_DISABLED` is not `1` (a global kill switch); and, with `--dry-run`, `--allow-paid-ai` is given (a dry run with art direction is a paid call). These checks happen before the brand profile is built, so a refusal costs nothing. While art runs, a lock file (`brands/<slug>/.autopilot.lock`, stale after 6 hours) allows one run per brand, and the plan, history and report files are written atomically.
What a run writes: `week-NN.json` in mode `art_v1` where every post carries `art` (candidates, first = chosen) and `approval: pending`, or `artFailure` with the reasons it has none; `art-report-week-NN.json` (status, counts, requests, flags, requested vs actual option and reasons per post); then the posters and `out/<slug>/week-NN/render-report.json`. An `art_v1` post without `art` is a failed render, never silently drawn by the older renderer; the older renderer is used for a failed art post only when `art.json` sets `fallbackToLegacy`, and the report then shows the failed art attempt plus `fallback: legacy`. Failed posters fail the run but the others are kept.
Review: rendered art posters are recorded in `history.json` (`weeks[].art`) as `pending` with the art record of what ACTUALLY rendered. Nothing is scheduled or exported until a person runs `node src/art-review.ts --brand brands/<slug> --plan week-NN.json --list`, then `--post p1 --approve [--by name]` or `--post p1 --reject --reason "..."`. Approval needs a verified art-directed render; a rejected poster stops counting towards variety (pending and approved posters steer the next shortlist). The scheduler and the publisher export skip unapproved posters of an `art_v1` plan.
Spending: the director reserves each request's worst-case cost (prompt tokens plus an assumed answer length at the model's listed price) against `maxCostUsd` before sending, refuses a model with no listed price when a cap is set, and counts `chatJson`'s own retries inside its two-request budget. The provider is not given a token limit, so a longer answer than assumed is only caught afterwards from the returned usage. Pictures are bought only after a candidate passed measurement, and never for pictureless posts.
Not built yet: the planner still writes the older image prompt and format for every post (trimming them for art runs would save tokens); there is no `--resume` for a run that crashed between steps (the plan file, atomic writes and per-prompt cached pictures make a re-run safe but it plans a new week); approval is a command-line step, not yet in the dashboard; no fonts are bundled so posters are `capture_complete`, not `render_verified`. Before this is turned on for a client: run it against approved test brands with a live model in shadow (nothing scheduled), review the posters by eye, and check the fallback and rejection rates in the reports across several weeks and brands.

### Evidence facts (what a post may state)

A brand can carry `brands/<slug>/facts.json`: what its site states, kept as the exact words on the page with their structure. It is built by the profile run (`src/analyze.ts`) or on its own with no model call:

```
cd scheduler/engine && node src/facts.ts --site https://example.com
```

Each page is read in headless Chrome under a policy that blocks the page's own scripts and the network, with the homepage's stylesheets applied. A fact is `usable` only when nothing in the structure makes it doubtful; otherwise it is `needs_review` with reason codes (target not guarantee, demo value, figure strip, customer result, several figures in one sentence, other language, shared tax note, table or toggle not confirmed, stylesheets missing, conflicting values, stale). Conflicting prices or trials of the same plan hold both facts. Commercial facts older than 30 days are held when read.

With usable facts, `autopilot` gives the writer each post's own one or two facts instead of the brand's free-text offer, rules and proof points; profile text that states a figure is left out; the claim gate checks every figure, price, period and qualifier against the post's facts. The plan says `evidenceCoverage: facts`. What is checked is recorded on each post (`evidenceChecks`): figures and qualifiers are checked by code; that the wording means what the source means is **not** verified (`semantic_support_unverified`). A brand without `facts.json` behaves as before and is `legacy`. A damaged `facts.json` stops the run rather than silently falling back.

A subline that only restates the headline or the identity line goes back to the writer once; after that it stays with a note (`editorial: ...`) for the reviewer. Other editorial findings are warnings only.

Owner review of facts: `node src/facts-review.ts --brand <slug> --list 25` shows the best-ranked candidates with ids; `--approve id,id` and `--reject id` record decisions in `brands/<slug>/facts-review.json`. Once anything is approved, posts are written from approved facts only; a rejected fact is never used; with no decisions every usable fact is eligible. Decisions are keyed by fact id, so a fact whose wording changed on the site is no longer approved.

Optional semantic check: `autopilot --semantic-check` (with `--dry-run` it also needs `--allow-paid-ai`) asks a model once per batch of posts whether each post's copy says more than the facts it was written from; a post judged stronger is left out, an undecided one stays with a note, a supported one is marked `semantic_support_model_judged` (still not proof). Answers are cached in `semantic-verdicts.json`. A post whose subline is exactly its headline or identity line after the second try is left out.

Visual strategy (v1): an AI picture is allowed for a post only when its accepted concept names a concrete subject and action and at least one word of that subject or action is in the post's own copy or concept (`src/visual-strategy.ts`). Otherwise the art director's shortlist holds only options that need no picture (typography, structured list, figure) and no image is generated or paid for. This is a cheap guard, not a judgement of relevance, and it reads concept fields the planner wrote. It is on by default (`pictureGate` in the art settings). The fit judge also warns `possible_unbalanced_composition` when content (text, brand element or picture) ends above 85% of the poster height; it only warns, and a cropped picture subject is not checked. Not built yet: unordered rows and connected-flow graphics (they need a source that states a list or an order, for example an `<ol>` or `<ul>` in the page, and must never imply an order the source does not give), approved product assets, and a short identity variant.

Known limits: a table is trusted as plan and attribute only when the plan name also appears as a heading or card title on the site; a monthly/yearly switch is noticed but only the shown variant is read; content hidden only by a stylesheet that could not be fetched may be read (those facts are held); headings count as facts only with a figure or commercial wording; the semantic verifier exists as a pure layer with an injected judge and is not connected to a live model.
