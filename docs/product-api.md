# Product API

How a product (such as Brandbasket) uses social-auto. Every call is made by the product's **server** with its own key; the key must never reach a browser.

```
Authorization: Bearer <product key>
```

## Settings (social-auto)

| Where | Name | Meaning |
|---|---|---|
| publisher | `ANALYTICS_ENABLED` | on by default; `false` switches off the daily check of the networks' numbers and `GET /api/v1/analytics` (which then answers `503 SERVICE_NOT_CONFIGURED`). The daily check itself runs from `social-analytics.timer`, which has to be installed and enabled on the server |
| publisher | `PRODUCTS` | JSON list: `{id, keyHash (SHA-256 hex of the key), returnUrls[], webhookUrl?, webhookSecret? (16+ chars)}` |
| publisher + dashboard | `INVITE_SECRET` | 32+ characters, the same value in both; signs connect links |
| publisher | `DASHBOARD_ORIGIN` | the dashboard's address, where connect links point |
| publisher + dashboard | `LINKEDIN_CLIENT_ID` (+ publisher `LINKEDIN_CLIENT_SECRET`) | the LinkedIn app |
| publisher + dashboard | `FACEBOOK_APP_ID` (+ publisher `FACEBOOK_APP_SECRET`) | the Meta app, for Facebook Pages |
| publisher + dashboard | `INSTAGRAM_APP_ID` (+ publisher `INSTAGRAM_APP_SECRET`) | the Instagram app of the same Meta app (Instagram API with Instagram login). Its redirect address is the dashboard's `/api/instagram-callback` |

## Endpoints (publisher)

- `POST /api/v1/workspaces` `{externalId, name, group?}`: creates the workspace (a brand), or returns the existing one. A customer may own several brands under one login: brand 1 keeps its own id as `externalId` and is its own `group`; further brands use another `externalId` (for example `<businessId>:<brandKey>`) with `group` set to the customer's id. The group is fixed when the workspace is made: another group for an existing workspace answers `409 GROUP_MISMATCH`; a bad group `400 INVALID_GROUP`. `PATCH /api/v1/workspaces` `{externalId, name?, autoPosting?}` renames it (or sets automatic posting, see [Automatic posting](#automatic-posting-patch-apiv1workspaces)) and answers `{workspace}` (the same shape as the read): the name is trimmed and cut at 80 characters, blank or missing is `400 INVALID_REQUEST`, a bad `externalId` is `400 INVALID_EXTERNAL_ID`, an unknown one (or another product's) is `404 WORKSPACE_NOT_FOUND`, a body over 2 KB is `413 REQUEST_TOO_LARGE`; the same name again is safe and a brand put away can still be renamed. **The name is only what screens show (yours and our staff dashboard): posters and captions take the brand's name from the customer's website and are not changed.** Creating a workspace again with another name does not rename it. `GET /api/v1/workspaces?group=` lists the customer's workspaces `{workspaces: [{id, externalId, name, website, archived}], brandsAllowed, brandsUsed, ceiling}` (only your product's; an unknown group is an empty list). The workspace read also has `archived` and `group: {id, brandsAllowed, brandsUsed}`. **A customer may have only as many brands as they are allowed** (1 by default; our team can allow up to 4, which is a fixed ceiling): a create beyond that answers `409 BRAND_LIMIT_REACHED` with a plain sentence ("You can have 1 brand. Ask us to allow more."). A group can also never hold more than 8 workspaces in all, archived ones included. `POST /api/v1/workspaces/archive` `{externalId, archived: true|false}` puts a brand away or brings it back: a brand put away is kept but **paused** (nothing new is sent, written or drawn: calls that write, draw or spend answer `409 WORKSPACE_ARCHIVED`; reads still work), it no longer counts toward `brandsUsed`, so it frees a slot, and bringing it back needs a free slot (`409 BRAND_LIMIT_REACHED`) and lifts only the pause that putting it away made, never one our team made. Doing either twice is safe. Our team sets the default and each customer's number in the social dashboard (Clients page, "Brands per customer"); the highest number, 4, is fixed in the code, and every change is logged with who and when. `GET ?externalId=` reads it with its channels (never tokens). The workspace and each channel carry `paused`: true when the team has paused the workspace, everything, or that account, so posts are not being sent there. It also carries, read only: `website` (the customer's website once they gave one, else null), `approvalMode` (always `manual`: the customer approves their own posters, and nothing in the API or in our dashboard can make it automatic) and `notices`, a list of `{code, channelId?, platform?, message}` in plain words for the customer: `CONNECTION_EXPIRING` (7 days or less), `CONNECTION_EXPIRED` (posts to that account are on hold until it is connected again), `ACCOUNT_DISCONNECTED` (`platform`; scheduled posts still ahead are aimed at a platform with no connected account, so they are on hold; the message says how many and that they go out once it is connected again if their time has not passed) and `PAUSED`. Posting plans cannot be added for a product's customer; their posts are made when they ask.
- `POST /api/v1/connect-link` `{externalId, channel: "linkedin" | "facebook" | "instagram" | "google", returnUrl?}`: a link (valid 1 hour) the customer opens to press Allow. `returnUrl` must be one of the product's registered `returnUrls`; the customer comes back to it with `?social=connected|denied|failed&channel=linkedin` (or `facebook`, `instagram`, `google`). A Facebook link connects every Page the customer chooses; each Page appears as its own channel id (`facebook:<page id>`). A Google link has the customer sign in with the Google account that manages their Business Profile; with one listing it is connected at once, with several a plain page asks which one is theirs (one listing per link, press it again to add another). Each appears as `google:<location id>` and is posted to as an update. Google drops hashtags and shortens text over 1500 characters, so the same caption reads a little differently there. A Google account with no listing comes back as `failed`. An Instagram link connects the customer's own Business or Creator account (no Facebook Page needed) as `instagram:<account id>`. Social-auto renews it every week, so it only ends if the customer removes the app or renewal fails, and then `connection.expiring` is sent.
- `POST /api/v1/pictures`: body is the JPG (square, 320-4096 px, up to 4 MB); answers `{pictureId}`.
- `POST /api/v1/posts` `{externalId, day: "YYYY-MM-DD", time?: "HH:MM", caption, pictureId, channels?, variants?}`: goes out that day at `time` (India time, default 10:00; a post with its own time is sent by the frequent run within about 5 minutes of it) to the chosen channel ids (default: all connected). The moment must be ahead of now and within 90 days. `variants` gives a platform its own caption or picture, see [Per-channel versions](#per-channel-versions-variants).
- `GET /api/v1/posts?externalId=[&from=YYYY-MM-DD&to=YYYY-MM-DD]`: all of the customer's posts, planned and extra, earliest first. Each has `id, date, caption, imageUrl?, manual, variants?, state` (overall) and `channels[]` (`id, platform, account, state, permalink`). `state` is one of `scheduled`, `due`, `published`, `missed`, `skipped` (the team skipped it, or its channel was paused when its time came, so it is never sent late) `paused` (held back by a pause for now) or `held` (every account or platform the post is aimed at is missing, see below; while another network is still to be sent the post stays `scheduled`, `due` or `missed` and the missing one shows only in `targets`). `from` is the first day and `to` the last day shown, in India time.
- `PATCH /api/v1/posts?externalId=&postId=` `{day?, time?, caption?, pictureId?, channels?, variants?}`: changes a post the product made (`manual: true`) while it has not gone out; anything left out stays. A scheduled post that was written and approved for the customer (not `manual`) can only be **moved**: send `day` and/or `time` (India time; without a day it stays on its day), and nothing else (`400 INVALID_REQUEST`). Its words and pictures stay, every network moves together, and the move survives the hourly release (it is kept apart from the schedule). It must still be ahead (`409 POST_NOT_EDITABLE`), the day must not already have another planned post of the customer (`409 CONFLICT`), and a time or day in the past answers `400 TIME_PASSED`/`DAY_PASSED`. Another customer's post, or one that does not exist, answers `404 POST_NOT_FOUND`. A post moved to its own planned day and time is back as planned. A moved post is sent by the frequent run at its time. Answers `{post}`.
- Each post also has `targets[]`: every account it is meant for (`id, platform, account, state, permalink`, and `code`), including accounts that were **disconnected**. A target for a disconnected account has `account: null`, `code: "ACCOUNT_DISCONNECTED"` and the state `held` while the post's time window is open (the post waits: connecting the same account again lets it go out), then `missed`. A post aimed at a whole platform (written and approved posts name the platform, for example `facebook`) gets the same kind of target when no account of that platform is connected any more: `id` is the platform name, `account: null`, `code: "ACCOUNT_DISCONNECTED"`. A post for every connected account (no accounts named) never has such a target. The `post.held` and `post.missed` events say the same (`channel` is the account id or the platform name).
- `POST /api/v1/send` `{externalId, postId}`: sends a post the product made right now (409 while it is skipped or paused), to its chosen channels, and dates it now. Answers `{post, failed, problems?}`; `failed: true` means a channel did not take it, and the post stays due for 20 hours so the next daily run tries again. `problems` lists each channel that failed as `{account, code, error}` (codes `CHANNEL_UNREACHABLE`, `RECONNECT_NEEDED`, `CHANNEL_REFUSED`; the channel's own error text is never passed on). Only the channels that failed are tried again. 409 when it has already gone out. Anyone's post that is not the product's own, and planned posts, answer 404/400.
- `DELETE /api/v1/posts?externalId=&postId=`: removes a post that has not gone out.
- `POST /api/v1/site-jobs` `{externalId, site, networks?, page?, weeks?, postsPerWeek?, weekdays?, startDate?}` and `GET /api/v1/site-jobs?externalId=[&jobId=]`: read a customer's website and write posts for it, see [Writing posts from a website](#writing-posts-from-a-website-site-jobs).
- `GET` / `PUT /api/v1/schedule` the days of the week each channel posts on (see below)

- `GET|POST /api/v1/posters`: the drawn pictures the customer approves or rejects, see [Pictures to approve](#pictures-to-approve).
- `GET|POST /api/v1/facts` and `GET|POST /api/v1/batches`: the facts found on the website and the written posts, which the customer decides on before anything is drawn, see [Facts and written posts](#facts-and-written-posts).

A product only ever reaches workspaces it created. Another product's customers answer "no such workspace" (`WORKSPACE_NOT_FOUND`).

## Writing posts from a website (site jobs)

`POST /api/v1/site-jobs` `{externalId, site, networks?, page?, weeks?, postsPerWeek?, startDate?}` starts a batch of written posts for a customer: the website is read and posts are written, with a caption for each network. **Nothing is drawn, paid for on the picture side, or published at this step.**

- `site` is the customer's website, like `acme.com` (with or without `https://`). **A customer keeps the first website they give**: a different one answers `SITE_MISMATCH`. `www.acme.com` and `acme.com` are the same website. With `page: true` only the page you give is read (for a customer's first website).
- `networks` is a list of `instagram`, `facebook`, `linkedin`, `google`. Left out, the networks the customer has connected are used; with none connected and none given the answer is `CHANNEL_NOT_CONNECTED`.
- `weekdays` is a list of days like `["mon", "wed", "fri"]`: the posts go out on exactly these days each week (so the posts a week are the days chosen, and `postsPerWeek` is ignored), the first on the first of them on or after `startDate`. Left out, the days the customer saved for her channels with `PUT /api/v1/schedule` are used; with none saved, the usual spread of `postsPerWeek`. Channels that were saved with different days cannot share one batch: start one batch per channel (`networks: ["instagram"]`), or the answer is `400 CHANNEL_DAYS_DIFFER`. A bad day is `400 INVALID_DAYS`.
- **The monthly plan:** a plan that came out short is topped up before the customer sees it: empty days are filled first from the drafts that passed review but were not chosen, then by writing the day once more, and a day nobody could write stays empty (told by `weeks[].missingDays` and the `empty` state). A batch is 4 weeks of 5 posts (Monday to Friday, 10:00 India time) by default, 20 topics, starting on the next Monday. `weeks` (1 to 4), `postsPerWeek` (1 to 5) and `startDate` (YYYY-MM-DD, tomorrow or later, within 180 days) may ask for less or another start; the ceilings are fixed by social-auto and anything above them answers `400 INVALID_REQUEST`. The pictures are drawn one week at a time (see `draw`). **Next month:** `GET /api/v1/batches` carries `plan: {startsOn, endsOn, canStartNext, nextStartDate}`: `endsOn` is the last post day of her plan (batches not put away, drawn ones included), `canStartNext` is true when she has no plan or the last post is within 10 days, and nothing is being written; `nextStartDate` is the Monday after the plan ends (or the next Monday). Start it with the same call and `startDate: nextStartDate`.
- **One page:** with `page: true`, `site` may be the address of one page (for example `https://acme.com/services`): only that page is read, and the saved website stays the host alone. The query and the anchor are dropped. A page can be read only for a website whose facts were not built yet; if they were, the job fails with `failure: "PAGE_MODE_UNAVAILABLE"` (use the whole website address). A first try that did not finish does not count: a page may be read again.
- Answers `202 {job, created: true}`. If a batch is already waiting or running for the customer, that job comes back instead (`200`, `created: false`), so pressing twice never starts two.
- A customer may start 3 batches a day and 10 a month; beyond that the answer is `429 JOB_LIMIT_REACHED`. A job that is still waiting is always returned.
- `X-Social-Actor` (optional here) names the person who asked, 1 to 64 letters, digits or `. _ : -`; it is recorded with the job.

`GET /api/v1/site-jobs?externalId=` lists the customer's jobs, newest first; with `&jobId=` it answers one `{job}` (an id that is not this customer's answers `404 JOB_NOT_FOUND`). A job is `{id, kind, state, step?, createdAt, finishedAt?}`:

- `kind` is `write` (a batch of written posts), `draw` (pictures: the first draw, a redraw, or the picture of a network added later) or `network` (the words for a network added to a batch).
- `state` is `queued`, `running`, `done` or `failed`; `step` is 1 to 4 while it runs (reading the website, writing, drawing, putting the results in review).

If the poster service is not available, the answer is `503 ENGINE_UNAVAILABLE`; try again shortly.

## Automatic posting (`PATCH /api/v1/workspaces`)

A customer may let the system post for her without approving each poster first. It is **her choice, per channel**: the workspace read has `approvalMode: "manual" | "auto"` (`auto` when it is on for at least one channel) and `autoPosting`, which is `null` when it is off, else `{channels: ["instagram", "facebook"], safetyHours: 24, consentedAt, needsChoice: ["linkedin"]}`. `needsChoice` lists the connected channels that are **not** automatic: a channel she connects later starts as manual, so ask her again (manual or automatic) for the channels listed there and send the new list.

`PATCH /api/v1/workspaces {externalId, autoPosting: {channels, safetyHours?, consent}}` sets the channels it is on for and answers `{workspace}`. It **replaces** the list: send every channel she wants automatic; `channels: []` switches it off (no consent needed, `X-Social-Actor` optional). `safetyHours` is a whole number of hours from 0 to 72 (default 24): the system approves a picture that passed the checks that many hours **before its posting time**, never earlier, so she can still open, change, reject or remove it until then (0 approves as soon as it passed the checks). Switching a channel on needs `consent: true`, sent only after she accepted your own consent text, and `X-Social-Actor` (the person who agreed, recorded with the time). `name` and `autoPosting` may come in one call. Errors: `400 CONSENT_REQUIRED`, `400 ACTOR_REQUIRED`, `400 CHANNEL_NOT_CONNECTED` (a chosen channel has no account), `400 INVALID_NETWORKS`, `400 INVALID_REQUEST` (bad `safetyHours` or shape), `404 WORKSPACE_NOT_FOUND`, `503 ENGINE_UNAVAILABLE` (nothing is saved then; send it again).

What the system then does for her, and only this, **with every automatic check still in force**: a written topic the checks gave no warning about is kept; the first week is drawn at once (later weeks on their Thursday, as always); a picture that passed the checks is approved inside the window, recorded as `auto-checks`, and reaches her calendar at once. **Always left to her:** a topic the checks warned about, a picture the checks blocked, carousels, and her own topic requests' words. The picture limits and the monthly spend limit apply as before. She can stop at any time with `channels: []`; posters already approved stay approved and she can still take them back (`reject`) until they go out.

## The days a customer posts on (`/api/v1/schedule`)

`GET /api/v1/schedule?externalId=...` answers `{schedule: {channels: {instagram: {days: ["mon", "tue", "sat"], nextWeek: ["2026-11-16", "2026-11-17", "2026-11-21"]}}}}`: only the channels that have days of their own, each with its days in week order and the dates a batch starting on the next Monday would give for its first week (India time).

`PUT /api/v1/schedule {externalId, channels: {instagram: ["mon", "tue", "sat"], facebook: ["wed", "fri"]}}` **replaces the whole setting** and answers like `GET`: a channel that is not listed goes back to the usual spread, and `channels: {}` clears it. Days are `mon` to `sun` in any letter case (`Monday` works), each once. Errors: `400 INVALID_DAYS` (an empty list or a day that is not a day), `400 INVALID_NETWORKS` (a channel that is not `instagram`, `facebook`, `linkedin`, `google`), `400 INVALID_REQUEST` (`channels` is not an object), `404 WORKSPACE_NOT_FOUND`.

The days are used when a batch is written (`POST /api/v1/site-jobs`, see `weekdays`): **a week already written or drawn never moves**, and changing them changes only batches started afterwards. A topic request still goes out on the day the customer picks, whatever her days are.

## Facts and written posts

Both need `X-Social-Actor` (the customer's person) to **decide**; reading works without it. Nothing here is drawn or paid for.

`GET /api/v1/facts?externalId=` answers `{builtAt, profile, facts: [{id, text, sourceUrl, sourceQuote, state, held}], counts}`. `state` is `suggested`, `confirmed` or `removed`; a `held` fact cannot be confirmed. Before the website has been read the answer is `404 NOT_FOUND`.
`POST /api/v1/facts` `{externalId, factId, action}` with `action` `confirm`, `remove` or `restore` answers the facts as they are now. A held fact answers `409 FACT_HELD`.

`GET /api/v1/batches?externalId=` answers the written posts still waiting: `{expired: [{id, expiredAt}], batches: [{id, createdAt, networks, signoffDefault?, posts: [{id, headline, caption, captions, state, edited?, signoff?, advice?}]}], networkRules}`. `expired` lists written batches that were put away because nobody decided in 14 days (shown for about 2 months so the customer can be told); `captions` is the text for each network; `state` is `pending`, `kept` or `dropped`; `advice` is a short note about the post; `networkRules` gives each network's length limits.
`POST /api/v1/batches` `{externalId, batchId, action, postId?, ...}`:

- `keep` or `drop` (needs `postId`): the customer's choice for one post.
- `edit` (needs `postId`) with any of `headline`, `caption`, `network` (change that network's caption), `brandName`, `domain` (the poster sign-off; an empty text leaves that line off). The words are checked against the facts found on the customer's website: `422 WORDS_NOT_ACCEPTED` when they do not agree. **What the check covers:** numbers, prices, percentages, deadlines, superlatives and market-position claims ("number one", "best", "leading"), vague quantities and endorsements ("thousands of", "award-winning") and guarantees are accepted only when a verified fact states the same thing. Other statements are not judged: the customer is responsible for what they write and approve.
- `close`: put the whole batch away.

- `draw` (optional `week`, optional `retry: true`): ask for pictures for the kept posts. **A batch written for several weeks is drawn one week at a time.** `GET /api/v1/batches` then gives each batch `weeks: [{from, to, state, postIds}]` (`from` is the Monday, `to` the Sunday, `state` is `waiting`, `drawing`, `drawn`, `not_drawn`, `lapsed` or `empty` (a week the plan was asked to write for and got no post; `missingDays` lists the days of a week that have no post)) and each post its `date`. `week` is the Monday of the week to draw; without it the first week not settled yet (waiting or being drawn) is meant, so asking again never starts the next week by accident, and the same week asked twice is the same job (`200`, `created: false`). The job has the `week`. Words and headlines of a drawn week are final; the later weeks stay open for keep, drop and edit until their own draw. **The system draws the later weeks by itself:** week 2 and later are drawn automatically on the Thursday before the week begins, at 10:00 India time, for the topics the customer kept in it, and only when the week still has room for the pictures; a week with nothing kept waits (a topic kept later is drawn at once) and a week that ends without a draw becomes `lapsed`. The first week is the customer's to ask for. Automatic draws are jobs with `auto: true` and do not count against her draw limit (`DRAW_LIMIT_REACHED`). Pictures are drawn only for the networks she has connected accounts for (we are told whenever she looks at her written posts or asks for pictures). **A kept topic that gets no picture** (its headline is too weak, no picture passed the checks, or a channel had no pictures left) is not lost: the week's draw ends as failed (`failure: "PARTIAL_DRAW"` or `"NOTHING_DRAWN"`), the post has `notDrawn: {code, message}` and its week lists it in `weeks[].notDrawn` (`code` is `HEADLINE_TOO_WEAK`, `NO_PICTURE`, `PICTURE_LIMIT_REACHED` or `FACT_OUT_OF_DATE`; `message` is a sentence to show). **The facts are looked at again when a week is drawn:** a month's plan is written at once and its last weeks are drawn weeks later, so a post that rests on a price or an offer older than 45 days at the time of the draw, or on a fact the customer took out (`remove` in `GET/POST /api/v1/facts`), is not drawn and gets `FACT_OUT_OF_DATE`. Putting the fact back (`restore`) and asking for the retry draws it; a fact she has not confirmed is still fine. A week whose draw ran but left every kept topic without a picture has `state: "not_drawn"`, not `drawn`. The topic is open again for `keep`, `drop` and `edit` (the headline too) while a topic that has its picture stays final, and `draw` with that `week` and `retry: true` draws only the topics still without a picture (it counts as one of her asks). The system never retries by itself.
- **A week is drawn by the post.** A draw makes final only the posts it draws; the rest of the week stays open (keep, drop, edit, move and replace still work on them) until their day passes, so she can keep a few topics, draw them, then keep more and draw again. Each `draw` covers the **kept posts that have no picture yet and whose day is tomorrow or later** (a kept post that was drawn and got no picture is drawn again); the same ask while that draw is waiting or running is the same job (`200`, `created: false`), so nothing is bought twice. When there is nothing to draw: `422 NOTHING_KEPT`; a channel with no pictures left answers `429 PICTURE_LIMIT_REACHED` (with `channel` and `restart`) and nothing is bought. **Read it from `GET /api/v1/batches`:** `weeks[].state` is also `partly_drawn` (some posts of the week were drawn and others are still open), and `weeks[].openPostIds` lists the posts that can still be kept, dropped, edited, moved or replaced (not drawn, day tomorrow or later); each post has `drawn` (it was sent to be drawn and has pictures, or are being made) and `locked` (its choice, words and day are final). The week becomes `drawn` when no open post is left or the week has ended (open posts of a week that ended are given up). **Keeping a post whose day is today or has passed answers `400 DAY_PASSED`.** The weekly (Thursday) draw of later weeks draws what she has kept by then and leaves the rest open: what she keeps after that is drawn only when she asks. Batches drawn before this keep the old rule for the week they drew (every post of it final). A customer may ask for pictures up to 10 times a day and 40 times a month (`429 DRAW_LIMIT_REACHED`), as a week may now be drawn in several rounds; the weekly pictures of each channel still bound what she can draw.
A week with nothing kept answers `422 NOTHING_KEPT`; a week already drawn `409 BATCH_LOCKED`; a `week` the batch does not have `400 INVALID_REQUEST`. **Every network gets a picture of its own** for each kept post: the same topic, headline and facts, but a different composition (square for Instagram, Facebook and Google, wide for LinkedIn), so four networks mean four pictures. A batch drawn before this keeps its pictures as they are (Instagram, Facebook and Google may share one square, shown by `sharedWith`). **A customer may draw 7 pictures a week for each channel** (5 for the week's posts and 2 spare for a redraw or a channel added in the week) (see `GET /api/v1/limits`): the week runs Monday to Sunday in India time and every picture drawn counts, a redraw and the picture of a network added later too, but a try that bought nothing does not. A draw that would pass a channel's limit is refused whole before anything is bought, with `429 PICTURE_LIMIT_REACHED` naming the channel and the day it starts again. Carousel slides are not counted here. A hard ceiling in the code on pictures per month can never be raised by a setting. **This is what costs money**, so it is limited: once per batch (a second ask returns the same job, `200`, `created: false`; `retry` only after a failed one), and per customer 3 times a day and 10 a month (`429 DRAW_LIMIT_REACHED`). Keeping nothing answers `422 NOTHING_KEPT`. Answers `202 {job, created}`; the job has `kind: draw` and the `batchId`, and follows the same states as a write job (`GET /api/v1/site-jobs`). The pictures then appear in `GET /api/v1/posters`.

- `add-network` (with `network`): write the words of **one more of her connected networks** for every topic of the batch, from the same topics (no website read, no new batch). It is a **job** (the words need the AI): `202 {job, created}` with `job.kind: "network"` and the `batchId`; pressing twice while it runs answers the same job (`200`, `created: false`). Follow it in `GET /api/v1/site-jobs`: a finished job has `result: {network, topics: [{postId, outcome: "written", fallback?: true, posterIds?, drawJobId?}]}`: every topic gets words for the new network; `fallback: true` means its own words could not pass the checks, so the main words adapted to the network are used (she can change them with the words check), and `reasonCode` says why: `WORDS_REFUSED` (the facts do not support them), `TOO_LONG` (over the network's limit), `NO_FACTS` (the topic names no facts to check against) or `NO_CAPTION` (nothing could be written); `drawJobId` is a drawing job (follow it in the same list) for a topic that was already drawn: every network gets a picture of its own, so the new network's picture is always drawn and never copied from another network's. A failed job has `failure` (a fixed code). For a topic already drawn, a new **waiting** picture for that network is drawn (about $0.017 each; it counts against her 7 pictures a week for that channel). **It is never refused for lack of pictures:** the words are written for every topic, the pictures are drawn only for the soonest topics that fit in this week's room (`drawJobId` is present for those), and the rest wait: their channel shows `pictureState: "limit_reached"` in `GET /api/v1/topics` and the system draws them as room comes (it asks again every few minutes, soonest topic first, and never for a topic whose day has passed or for a network that is not connected; a try that failed for another reason is left to the customer). Automatic draws are not counted against her own asks. On a batch of several weeks only a topic whose day has not passed gets a picture drawn now; a topic whose week is not drawn yet gets its picture for the new network in its own week's draw, and one whose day has passed gets none. She approves only that network's new picture; nothing already approved changes. Errors: `400 INVALID_NETWORKS`, `400 CHANNEL_NOT_CONNECTED` (no account of that platform), `409 NETWORK_ALREADY_THERE`, `409 BATCH_LOCKED` (closed or expired), `404 NOT_FOUND`, `503 ENGINE_UNAVAILABLE`.
- `replace` (with `postId`, of a post she **dropped**): gives it a **new topic**. A job (`kind: "replace"`, with `batchId` and `postId`; `202 {job, created}`, or `200` with the job already waiting or running for that post, `created: false`; follow it in `GET /api/v1/site-jobs`, so a screen can say "writing a new topic") that writes one new post for the **same day and time**, from the website's facts, through the same writer and checks as every other post (the claim gate, the brand-identity check, the headline rules), told not to repeat any post of the batch, dropped one included. It is written for the networks the dropped post was written for and she has connected. When the job succeeds the batch has the new post: a new `id`, state `pending`, `replaces` = the dropped post's id (and the dropped post shows `replacedBy`); she keeps, edits or drops it with the usual calls. **Words only: no picture is drawn or paid for until she keeps it and asks for pictures.** A week may have **3** new topics (`weeks[].replacementsLeft`): the fourth is `429 REPLACE_LIMIT_REACHED` with `restart`, the Monday she can ask again; asks that are still being written count. A try that writes nothing passes no check and **fails with `failure: "NOTHING_WRITTEN"` and is not counted**. Only for a dropped post (`409 CONFLICT`; also for one that already has a new topic), of a week not drawn yet (`409 BATCH_LOCKED`), whose day is tomorrow or later (`409 DAY_PASSED`); `404 NOT_FOUND` for no such post. `X-Social-Actor` is required; a brand that is put away answers `409 WORKSPACE_ARCHIVED`.
- `move` (with `postId` and `day`): moves a written post to **another day of its own Monday-to-Sunday week**, in any state (pending, kept or dropped), until that week is drawn: this is what dragging a topic to another day column does. `day` is `YYYY-MM-DD`; the **time stays as the post has it**; two posts may share a day. The day is changed in the batch and in the plan the pictures, the approval and the sending come from, so the post goes out on the new day. Answers `200 {batch}` (the batch as it is now), plus `warnings: ["WORDS_NAME_A_DAY"]` when the post's words name a weekday or say today, tonight or tomorrow: **the words are not rewritten**, so she should read them again. Moving to the day it already has is a `200` that changes nothing. Errors: `400 INVALID_DAY` (not a real day, or outside the post's own week, the Monday after included), `400 DAY_PASSED` (today or earlier, India time), `409 BATCH_LOCKED` (its week was drawn or the batch put away: the day is final once pictures are asked for), `404 NOT_FOUND`, `409 WORKSPACE_ARCHIVED`, `400 ACTOR_REQUIRED`. A post that is already approved and scheduled is moved with `PATCH /api/v1/posts` instead.

The other actions each answer `{batch}` as it is now. Once pictures have been asked for, or the batch was put away, the choices are final: `409 BATCH_LOCKED`.

## Topics

`GET /api/v1/topics?externalId=` answers `{topics: [{batchId, postId, headline, networks: [{network, status, pictureState, drawsOn?, notDrawn?}], missing: [...]}], connected: [...]}`. **`pictureState`** says what each channel's picture of the topic is doing, in a fixed vocabulary: `ready` (waiting for her decision), `approved`, `rejected`, `blocked`, `held`, `expired`; or, with no picture yet: `needs_connection` (the account is not connected, so nothing is drawn for it), `drawing` (its week is being drawn), `limit_reached` (no pictures left this week for the channel), `not_drawn` (its week was drawn and this topic got none: `notDrawn: {code, message}` says why) or `waiting` (its week is not drawn yet; `drawsOn` is the day the system draws it, absent for the first week, which is her button). A topic is one post idea. `networks` are the networks it already has: `status` is `written` (words only, not drawn yet) or the status of that network's newest picture. `missing` lists the customer's connected networks the topic does not have yet (so a product can offer "add Facebook to this topic"); it is empty for a topic that was put away unanswered. `connected` is every platform she has an account on.

## Pictures to approve

`GET /api/v1/posters?externalId=` lists the pictures waiting for the customer: `{posters: [{id, batchId, postId, network, shape, width, height, headline, caption, versionNumber, status, notice?, sharedWith?, canRedraw, redrawsLeft, createdAt}], reasons}`. `sharedWith` lists the OTHER networks whose current picture of the same post is the very same drawing (Instagram, Facebook and Google share one square drawing; LinkedIn's wide one is its own); it is left out when none. A redraw makes a different image, so a redrawn picture stops being shared with the others; a picture added for a new network that reuses another's drawing shares it. `&status=` is `pending` (default), `approved`, `rejected`, `blocked`, `superseded`, `held`, `expired` (put away because nobody decided in 14 days; these also appear as `expired` under `rejected` and `all`), `open` (pending and held) or `all`. A picture that did not pass the checks is `blocked` and cannot be approved; a `held` one needs the customer to confirm again. For both, `notice` is a plain sentence to show the customer, and `canRedraw` says whether one more picture can be drawn. A newer version of the same post and network makes the older one `superseded`.
**The day and time on every picture:** each poster (list and single) has `date` (`YYYY-MM-DD`) and `time` (`HH:MM`), India time: the day and time its post is planned for, read from the plan the pictures come from, so a post moved with `action: "move"` shows its new day, and a picture can be labelled "Mon 16 Nov 10:00" after its week is drawn and its batch no longer lists the post. Left out when the plan does not say. (A post that was approved and scheduled and then moved with `PATCH /api/v1/posts` keeps the planned day here; `GET /api/v1/posts` has its actual day.) Each written post in `GET /api/v1/batches` also has `time` next to `date`.

`GET /api/v1/posters?externalId=&id=` answers `{poster}` with, in addition, `ctaUrl`, `evidence` (where each fact the picture states was found: `{text, quote, url}`), `decidedAt` and `history` (earlier versions). With `&image=1` it answers the picture itself (JPEG).

`POST /api/v1/posters` (needs `X-Social-Actor`; repeating a decision gives the same answer):

- `{externalId, action: "approve", id}`, or `"reject"` with `reason` (one of the `reasons`) and optional `comment` (500 characters), or `"withdraw"` to take back an approval: answers `{decision: {id, status, decidedAt}}`. A withdraw also stops the post if it is already in the schedule and no other network of it is approved (`postStopped: true`); with another network still approved, the other one is kept and the withdrawn one leaves at the next hourly pass. A post that has already gone out cannot be withdrawn (`409 POST_ALREADY_SENT`). Approving again lets a stopped post go ahead; a skip made by our team is never undone that way.
- `{externalId, action: "redraw", id}` draws one more picture for that network of the post: **once per poster** (`canRedraw`, `redrawsLeft`). Not while it is approved (withdraw first: `409 CONFLICT`). Beyond the allowance `409 REDRAW_LIMIT_REACHED`. It counts against the customer's draw limit (`429 DRAW_LIMIT_REACHED`) and against her 7 pictures a week for that channel (`429 PICTURE_LIMIT_REACHED`). Answers `202 {job, created}`; the new picture arrives as a new waiting picture (`poster.ready`), and the old one becomes `superseded`.
- `{externalId, action: "approve-topic", batchId, postId}` approves every network's waiting picture of one topic: `{decisions: [{id, status, decidedAt}]}`.

**Expiry.** A batch written for several weeks never expires by age: each topic lives until its own post day, and a week that passes undrawn is given up by us (`lapsed` in `weeks`). A picture waiting for a decision expires 14 days after it was drawn or at the end of its post day (India time), whichever comes first. A batch with no days, or a picture with none, keeps the 14 days. A written batch or a picture that nobody decides on in time is put away by us (no staff action): the picture then shows `status: "expired"` in `GET /api/v1/posters?id=`, and the customer can start a fresh batch. Two days before, the product gets `poster.expiring`; when it happens, `poster.expired` (see Webhooks).

A picture that did not pass the checks (`blocked`) cannot be approved, but the customer can put it away: `reject` with `reason: "other"` answers `200` and the picture moves to `rejected` (repeating gives the same answer). After the one redraw is used, that is the customer's way to clear it.

- `{externalId, action: "change-words", id, caption}` changes the words of that network's picture. It makes a **new waiting version of the same picture** (no new picture is drawn, nothing is bought, no redraw is used) that replaces the older one, even an approved one, and the customer must approve it again. Answers `{poster, postStopped}` (`poster` is the new waiting picture). The headline is printed on the picture, so it cannot be changed here (`400 INVALID_REQUEST`; a new headline needs a new picture). The words are checked like a written-post edit (facts, the network's length): `422 WORDS_NOT_ACCEPTED`; the same words as now: `400 NOTHING_TO_CHANGE`; empty or too long: `400 CAPTION_REQUIRED` / `CAPTION_TOO_LONG`; a blocked picture `409 POSTER_BLOCKED`; an old version `409 POSTER_SUPERSEDED` (change the newest); a post that already went out `409 POST_ALREADY_SENT`. If the old approval was already in the schedule, the post is stopped at once (`postStopped: true`) so it cannot go out with the old words, and goes ahead once she approves the new words **and** the hourly release has put them in the schedule: an approval answers `waitingForRelease: true` until then (and the next cron run lets it go). With another network of the post still approved, that network keeps going out and the changed one leaves at the next release.

Only the customer decides. A picture replaced by a newer one answers `409 POSTER_SUPERSEDED`, one that did not pass the checks `409 POSTER_BLOCKED`, and a withdraw of something that was never approved `409 CONFLICT`.

## Pictures a customer may still draw (`GET /api/v1/limits`)

`GET /api/v1/limits?externalId=` answers `{week: {from, to, restart}, limit: 7, channels: [{network, limit, used, left}]}` for her own workspace (`WORKSPACE_NOT_FOUND` otherwise). The week runs Monday to Sunday in India time and starts again on `restart` (YYYY-MM-DD). A customer may draw 7 pictures a week for each channel (5 for the week's posts and 2 spare). Every picture drawn counts, including a redraw and the picture of a network added later; a try that bought nothing does not, and carousel slides are not counted here. Draws, redraws and added networks that would pass a channel's limit are refused before anything is bought with `429 PICTURE_LIMIT_REACHED` (`error` is a plain sentence to show, for example "You have used your 7 Instagram pictures for this week. You can draw more from Monday 16 November."; `channel` and `restart` are fixed). Our own clients are not limited this way.

## The carousel of the week (`/api/v1/carousels`)

One post of 3 to 5 slides, with the **same slides on every connected channel** and the words written for each channel. It replaces one of the week's posts, is made from the facts the customer's website states (read it first: start a batch), and the business name is never written on a slide (the address and the real logo are on the last slide only). Google Business gets the first slide as a normal post.

- `POST /api/v1/carousels {externalId, action: "make", networks?, startDate?}` asks for it. Only connected channels are made for (`400 CHANNEL_NOT_CONNECTED` when there is none; `409 CONFLICT` before the website was read). `202 {job, created}`; the job has `kind: "carousel"` and follows the same states as a write job. A second ask while one is being made returns the same job (`200`, `created: false`).
- **One carousel a week** that is still wanted (waiting, approved or posted); a rejected one may be made once more, and no more than two are made in a week (Monday to Sunday, India time, from the day it is for). Beyond that `429 CAROUSEL_LIMIT_REACHED {error, code, restart}`; `error` is a sentence to show and `restart` the day she can make another. It costs about 9 cents for five slides, and is not counted in the 7 pictures a week for each channel (`GET /api/v1/limits`).
- **Weekly, by itself:** `POST /api/v1/carousels {externalId, action: "weekly", enabled: true | false}` (`X-Social-Actor` required) switches the weekly carousel on or off; answers `{weekly}`. It is off until the customer turns it on. While it is on, the system makes one carousel each week on the Thursday before it, at 10:00 India time, for the Friday of that week, and it waits for her approval like any other (`auto: true` job, by `system:weekly-carousel`; it does not count as one of her asks). It is made only when her website was read, a channel is connected and she has a written batch; it follows the one-a-week limit; and a week that was asked for once (even if the try failed) is not asked for again by the system. The release record is made with the carousel, so an approved one reaches every channel she connected.
- `GET /api/v1/carousels?externalId=` lists them, newest first: `{carousels: [{id, topic, date, count, status}], weekly}`. `status` is `incomplete` (not every slide is ready), `pending` (waiting for the customer), `approved`, `rejected` or `blocked` (a slide did not pass the checks).
- `GET /api/v1/carousels?externalId=&id=` shows one: `{carousel: {id, count, status, slides: [{position, status}], captions: [{network, caption, status}]}, reasons}`. The slide itself is `&slide=N&image=1` (JPEG). A slide or a caption of a carousel is never listed in `GET /api/v1/posters` and cannot be approved, rejected or redrawn there.
- `POST /api/v1/carousels {externalId, action: "approve" | "reject", id, reason?, comment?}` decides the **whole carousel** (every slide and every channel's words, exactly as they are now). `X-Social-Actor` is required. `reject` needs a `reason` (as for pictures). Answers `{carousel: {id, status}}`. A carousel that is not approved by its day is not posted.

## A topic in the customer's own words (`/api/v1/topic-requests`)

She writes what this week's extra post is about (an offer, a new dish, an event) and gets one post for one day. It is written from her words only (the website's facts and the brand's offer are not mixed in); her words are kept as she typed them and are **never called verified**: the post may only say what she wrote, and a figure, price or date she did not write is turned back by the same claim gate as every other post. Claims that need proof (a guarantee, a "best", a certificate, a result, a count of customers, a comparison) and links are refused up front.

- `POST /api/v1/topic-requests {externalId, text, week?}` (`X-Social-Actor` is recorded when sent) answers `202 {request}`, or `200` with the same request when the same words were already asked for the same week (no second job, nothing written or spent twice). `text` is 10 to 1000 characters, trimmed, no links (an address with http, `www.`, a bare domain such as `shop.in` or `name.com`, or an email address is refused). The same words for the same week, whatever their letter case or spacing, are the same request. `week` is a Monday (`400 INVALID_REQUEST` otherwise): the post goes out on the first day of that week she can still use (tomorrow or later, India time, 10:00); without `week`, tomorrow. A week that is over is `400 DAY_PASSED`. The customer's website must have been read (`409 CONFLICT`), at least one channel must be connected (`400 CHANNEL_NOT_CONNECTED`), and a brand that is put away answers `409 WORKSPACE_ARCHIVED`. It is written for the connected channels only.
- **Refused text:** `400 LINK_NOT_ALLOWED`, or `400 TEXT_REFUSED` with `reason`: `TOO_SHORT`, `TOO_LONG`, `NEEDS_PROOF` or `NOT_TEXT`. Nothing is started and nothing is kept.
- **One topic a week** (Monday to Sunday, India time, counted from the day of the post; one that failed does not use the week): `429 TOPIC_LIMIT_REACHED` with `restart`, the Monday she can ask again.
- `GET /api/v1/topic-requests?externalId=[&id=]` answers `{requests: [...]}`, newest first, the last ten, or `{request}` for one `id` (`404 NOT_FOUND` for none, including an id that belongs to another of the customer's brands; a malformed id is `400 INVALID_REQUEST`).
- **A request:** `{id, week: {from, to}, goesOutOn, goesOutAt, state, reason?, createdAt, batchId?, postId?, words?: {headline, captions: {<network>: text}}, picturesToDraw}`. `state` is `writing`, `waiting_for_words` (the words are ready for her to read, edit and keep), `drawing`, `drawn` (its pictures wait for her approval like any other, in `/api/v1/posters`) or `not_made`, with `reason`: `NOT_WRITTEN`, `TEXT_REFUSED` (the words could not be written within what she said), `DROPPED`, `PUT_AWAY`, `WEEK_PASSED`, `DRAW_FAILED`, `NO_PICTURE_ROOM` (no pictures left this week for one of the channels; it stays open and can be drawn again later), `NO_PICTURE`, `HEADLINE_TOO_WEAK` or `FACT_OUT_OF_DATE`.
- **Confirming and drawing** use the written-posts calls (`/api/v1/batches`): the topic is a batch of its own with one post (`batchId`, `postId`), so she keeps, edits and draws it there like any other post. **It is a unit of its own:** drawing it never locks the week's other posts, and a week she already drew never locks it. Her words must be kept before pictures are drawn; nothing is drawn before she asks.
- **Cost:** `picturesToDraw` is the pictures drawing it would make now (one for each connected channel it is written for), shown before she confirms. They count against each channel's weekly pictures (`GET /api/v1/limits`; a channel with none left answers `429 PICTURE_LIMIT_REACHED` on the draw).

## Per-channel versions (`variants`)

A post has one main caption and picture. `variants` gives one platform its own caption, its own picture, or both. It is an object keyed by platform (`instagram`, `facebook`, `linkedin`, `google`); any other key is refused (`INVALID_VARIANTS`).

```
POST  { ..., "caption": "Fresh laddoos this Diwali.", "variants": { "linkedin": { "caption": "Diwali is our busiest season." } } }
PATCH { "variants": { "instagram": null, "linkedin": { "caption": "New words." } } }
```

- Each platform's value is `{caption?, pictureId?}`. Only the platforms that differ need to be listed; a platform without a version, or a version that leaves a field out, uses the main caption or picture.
- `pictureId` is optional and works like the main one: a picture added through `POST /api/v1/pictures` (square JPG). A product that only wants different words sends captions only.
- On `PATCH`, a platform left out stays as it is, `null` puts the platform back on the main caption and picture, and inside a platform a field left out stays while `null` or `""` removes it. A version with neither a caption nor a picture is dropped.
- A variant caption follows the same rules as the main one (`CAPTION_TOO_LONG`, `TOO_MANY_HASHTAGS`).
- `GET` and the answers of `POST`/`PATCH` show `variants` only for the platforms that have their own version, as `{caption?, imageUrl?}`.

## Analytics

`GET /api/v1/analytics?externalId=[&from=YYYY-MM-DD&to=YYYY-MM-DD]` (default: the last 30 days, at most one year) gives the numbers the networks report for a customer's connected accounts and for the posts we sent. Read only; your own workspaces only (`WORKSPACE_NOT_FOUND` otherwise). A daily check on our side asks each network once a day, so numbers are up to a day old; nothing is ever written to a network. If analytics is switched off on the server the answer is `503 SERVICE_NOT_CONFIGURED`.

```
{ "channels": [{ "channel", "platform", "label", "status": "ok" | "waiting" | "reconnect" | "unsupported", "lastCheckedAt" }],
  "posts":    [{ "postId", "channel", "platform", "permalink", "postedAt", "caption",
                 "total": { "reach", "views", "likes", "comments", "shares", "saves", "clicks" },
                 "series": [{ "date", ...the same numbers, counted since the post went out }] }],
  "accounts": [{ "channel", "platform", "label", "checkedAt",
                 "series": [{ "date", "reach", "views", "profileViews", "followers", "calls", "directions", "websiteClicks" }],
                 "searchTerms": [{ "term", "impressions" }], "needs": ["reconnect" | "followers"] }],
  "audience": { "instagram"?: { "status": "ok", "age"?, "gender"?, "country"?, "city"? }
                            | { "status": "too_few_followers", "followers": 64 | null } | { "status": "reconnect" } | { "status": "none" } },
  "hashtags": [{ "tag": "#diwali", "posts", "avgReach" }], "checkedAt" }
```

- **`channels`** has one entry for every account connected for the workspace: `ok` (numbers exist), `waiting` (connected, first daily check not done yet), `reconnect` (the customer must connect the account again to give the permission to read its numbers; likes, comments, shares and followers may still show), `unsupported` (this network gives no numbers: LinkedIn). `lastCheckedAt` is that account's last check (`null` before the first); the top-level `checkedAt` is when the last whole daily check finished.
- **`audience.instagram`** (the workspace's first Instagram account; absent when none is connected): `ok` with lists of `{label, value}` (largest first; `age` and `gender` as percentages of followers, `country` and `city` as Instagram reports them), `too_few_followers` with the follower count (Instagram gives the audience from 100 followers), `reconnect`, or `none` (nothing yet). Facebook gives no audience, nor does Google.
- **A number a network does not give is absent, never 0.** Instagram and Facebook give per-post numbers; Google gives account numbers only (`views` = Maps and Search together, `calls`, `directions`, `websiteClicks`, `searchTerms` for the last full month) and nothing per post. Only posts we sent to Instagram or Facebook appear in `posts`, from the last 60 days.
- **Per-post totals:** `total` is the post's numbers since it went out (each field from the newest day that has it). A post is listed when it was made inside the range, and its `series` then covers its whole life so far, not only the range.
- **Dates** are UTC calendar days (`YYYY-MM-DD`), `from` and `to` inclusive; `postedAt` is an ISO time so you can show it in any time zone. Series are sorted oldest first; a day we have no reading for is simply absent (we read a post daily for its first week, then weekly). `from` after `to`, a bad date or a range over a year answers `400 INVALID_REQUEST`.
- **`hashtags`** is worked out by us: for each hashtag used by posts made in the range (with the leading `#`), how many posts used it and the average reach of those that have a reach number.

## Webhooks (social-auto to the product)

`POST` JSON to the product's `webhookUrl` for each event. Every event is written to a log first, so none is lost: a delivery that is not answered with a 2xx is tried again after 1 minute, 5 minutes, 30 minutes, 2 hours and 6 hours (6 tries in all, started by the cron), then given up on. The same events can be read at any time (see [Catching up](#catching-up-events)), so a product that was down loses nothing. An event can arrive more than once, or both by webhook and when read: **handle each `id` once.**

```
X-Social-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>" with webhookSecret>
X-Social-Event: post.published | post.failed | connection.expiring | job.finished | poster.ready | poster.auto_approved | week.drawing | week.drawn | week.lapsed
{ "id", "seq", "type", "createdAt", "data": {...} }
```

Check the signature over the **raw** body and reject a `t` more than 5 minutes old. Data: `poster.auto_approved` (the system approved a picture because she chose automatic posting for its channel; sent once, so she can look at it and take it back before it goes out) has `externalId, posterId, batchId, postId, network` and the planned `date` and `time` when known, and the picture shows `autoApproved: true` in `GET /api/v1/posters?status=approved`. `week.drawing`, `week.drawn` and `week.lapsed` (a week of a batch whose pictures are being drawn, were drawn, or were given up undrawn) have `externalId, batchId, week` (the Monday) and `jobId` or `lapsedAt`; `post.published` has `externalId, postId, channel, account, permalink`; `post.failed` has the same with `error`; `connection.expiring` has `externalId, platform, account, daysLeft (7, 3, 1 or 0), expiresAt`. `job.finished` (a batch of written posts, or a draw, ended) has `externalId, jobId, kind (write or draw), state (done or failed), batchId?`. `poster.ready` (a picture is waiting for the customer's decision) has `externalId, posterId, batchId, postId, network`. `poster.expiring` (a waiting picture or written batch will be put away in 2 days) has `externalId, kind (poster or batch), batchId, postId?, network?, posterId?, expiresAt`; `poster.expired` (it was put away because nobody decided in 14 days) has the same with `expiredAt` (when it was put away) instead of `expiresAt`; for a written batch (`kind: "batch"`) there is no `postId`, `network` or `posterId`. `post.held` (a post is due but an account it was aimed at is no longer connected, so it waits) has `externalId, postId, channel, platform, date, code (ACCOUNT_DISCONNECTED)`; `post.missed` (the post's window passed without it going out) has `externalId, postId, channel, account, date`. Each is sent once per post and account. The last six are found by the cron, so they arrive within a few minutes, not instantly.

### Catching up (events)

`GET /api/v1/events?after=<seq>&limit=<1..100>` answers `{events: [{seq, id, type, createdAt, data}], hasMore}`: this product's events after the one with that `seq`, oldest first (leave `after` out to start from the beginning). Remember the last `seq` you handled. Events are kept for 14 days. Use it on start-up and after any time your webhook address was down.
